## 二、缺口（按优先级；每条含验收与风险）

### ✅ P1 — 任务级验证器（"这轮算不算完成"的机械定义）· **2026-09-29 已完成（第 2 步）**

**原现状**：每步工具有自检，但"任务是否完成"仍主要信模型自报（刚修过"自称已完成、正文 0 字"）。

**已做的**（`sidecar/agent/task_verify.py` + 三处接线）：

- **判据只来自本轮自己的工具账本**（不解析用户意图 → 不猜任务类型就不会误伤）。
  账本在**全循环唯一的工具执行入口** `tool_exec._handle_tool_execution` 记（云/本地、
  串行/并行、四条早退路径都在此交汇），每轮 `begin_turn` 清空。
- 三类可机检终点：① `write_file` 产物**存在 + 非空 + 结构下限**（.json 能解析、
  .xlsx/.docx/.pptx 是带 `[Content_Types].xml` 的 ZIP、.pdf 有 `%PDF` 头且有 `%%EOF`）；
  ② 测试类命令（pytest/jest/npm test/cargo test…）**最后一次运行**的退出码/失败数；
  ③ 正文里"已保存到 /…/x.xlsx"式声称的路径**必须真实存在**。
- **白名单闸**：本轮没有 `write_file`/`run_cmd` → `verify()` 返回 `None`，开放问答零行为变化
  （"帮我分析今天大盘"没有机械验收，不强行套）。
- **两级生效**（策略在 `agent/loop.py` 交付路径）：第一次未达标 → 尾部消息要求"补齐并重新验证
  或如实说明卡在哪里"（重采一次）；第二次仍未达标 → **交回用户**并写明具体缺口，
  绝不把"已完成"留给用户自己发现。收口轮（终答轮）不再重采，改为交付时**明说没达标**。
- **反作弊**：本轮**删/清空**测试文件 → `hard`（不给重采，直接交回）；**改写**测试文件且同轮
  **先红后绿** → `soft`（可能真是测试写错了，允许解释一次）。正常新写测试（无红→绿转折）不拦。
- **不吞记账**：本模块只读账本、不写任何计数器；判定点在交付前，本轮的检索计数/信息增量
  已在工具执行阶段完成（施工约束 1）。

**验收证据**（`sidecar/tests/test_task_verify.py`，18 条）：
- 三类任务 × 三条路径：写文件（存在/缺失/空/半截 JSON）、指定格式（好 xlsx vs 假 xlsx、截断 PDF、
  声称路径不存在）、跑测试（红+宣称完成 → 拦；**红+如实说明 → 不拦**；先红后绿 → 通过；非测试命令失败 → 不拦）、
  作弊（`rm tests/test_x.py` → hard；清空测试文件 → hard；改测试+先红后绿 → soft；正常写测试 → 通过）；
- 开放问答：无产出型工具 → `None`（零行为变化，循环集成例同证）；
- **循环集成**：真实 `write_file` 写出半截 JSON → 第 1 次提示（提示进消息流，模型确已收到）→
  第 2 次交回用户（事件含"不按「完成」交付"+ 具体缺口），且 **≤5 轮收手、不空转到 40 步**；
- **A/B**：把 `loop.py`/`tool_exec.py` 回退到改动前跑同两条集成用例 → 未达标那条**红**
  （旧代码把"任务已完成"照单交付），开放问答那条两边都绿（证"零行为变化"不是嘴上说的）；
- 全量：`1194 passed, 1 skipped`（CI 同款 venv）。

**没做/已知边界（诚实记录）**：
- 「指定格式交付」只到**结构下限**，不校验字段级 schema（要 schema 就得给每类产物定契约，另行设计）；
- 「改测试文件+先红后绿」是**启发式**，所以只给 soft；判"改测试=作弊"会误伤"测试本来就写错"的真实场景；
- **未经真模型端到端实测**：判据与接线由真实工具执行 + 桩引擎的循环集成用例覆盖，
  但"模型在真实对话里被提示后是否改对"要看用户实际使用（热更已就位，重启应用生效）。
- 有意**不引入 LLM 裁判**（本地模型不可靠；见第三节"不做"表）。

**对照主流（2026-09-29 核查）**：ZCode / OpenClaw / Hermes 三家均**没有**任务级验收器——
它们的「验证」是 agent 自己跑测试/构建 + 人在环审批 + skills（Superpowers 那类提示词 SOP）。
含义有两层：① 辣条做 P1 会**领先于**主流；② **没有现成作业可抄**，所以上面四条约束
（尤其「白名单」与「两级生效」）不是保守，而是必要的安全垫。

**原缺口一句话**：没有对**目标**的机械验收——文章 CI 例子里的"测试全绿才算完"在辣条没有对等物；
也没有"不得通过破坏被验对象达成目标"的防线（删掉失败的测试让 CI 变绿）。**不动的后果**：幻觉成功换个形态还会回来。

### ✅ P2 — 验证结果反哺停止条件（组件咬合）· **2026-09-29 已完成（第 1 步）**

**原现状**：`verify_failed` 影响当轮话术，但不直接改变"停不停"——连续验证失败与单次失败待遇相同。

**已做的**：`_scan_tool_failures`（`agent/loop.py:1176`）在**轮首**扫描上一轮新落进消息流的工具结果，
既认硬失败（`tool_exec._looks_like_tool_failure`）**也认校验器的 ❌ 行**——签名取检查项名
（如 `verify:回读比对`），同一签名累计 **3 轮**且本轮未升级过 → 走**已存在**的硬升级通道交回用户。
仍是"按轮去重 + 轮首扫描不吞当轮记账"，没有新造机制。

**验收证据**：`sidecar/tests/test_compaction_reliability.py` 前 3 条（连续 verify ❌ 三轮升级、
正控——非失败头部不误伤、不同检查项不合并签名）；旧实现（只认硬失败）下 **3 条全红**、新实现全绿。

**风险**：低（复用已验证的通道）。

### 🟡 P2 — 压缩可靠性（2026-09-29 对照主流后新增）· **已完成第 1b 步的收口部分**

**原现状**：compaction 只是「压完就继续」（`agent/plugins/builtin.py` 各分支均 `return payload`，
没有质量校验、也没有失败回退）；压缩前**没有**提醒模型把要点存档。

**对照**：OpenClaw 在这块是三者里最讲究的——压缩保持 tool_call/结果**配对**；`safeguard` 模式做
**摘要质量审计**（必需标题/待办/精确标识符必须在）；不合格只给有限次修正，**仍不合格就放弃压缩、
保留原历史**；压缩前主动提醒 agent 把要点写进 memory 文件。

**已做的（2026-09-29）**：
- [x] **轮内工具结果按整行截断**（`_truncate_keep_lines`）：旧 `c[:300]+"…"+c[-100:]` 会从行中间切开，
  数字/文件名被劈成两半（模型可能把 `1376.55` 引成 `137`）；现在只在行边界切，标记里写明
  **省略多少行/多少字符**；
- [x] **少数极长行主导时按分隔符切**（压缩过的 JSON / 单行 CSV 整行取等于没压）：切点取窗口内最靠边界
  的分隔符；`_KEEP_HARD_MAX=2000` 保证"一行都没丢且体量本来就小"时**原样返回**（不动刀、不加噪音标记）；
- [x] **压缩后四语尾部提示**（本地/云端两分支都追加）：明示更早历史已压缩 + **不要凭记忆复述具体数字，
  需要就重新调用工具**（`messages.compaction_notice`）。
- 测试 `test_compaction_reliability.py` 后 6 条；旧实现下 **4/5 红**（第 5 条测的是本地化提示，与截断无关）。

**仍未做（且部分不适用——诚实记录）**：
- 「摘要质量审计 / 不合格放弃压缩」两条**对辣条不适用**：我们**没有 LLM 摘要压缩**，本地分支是
  `_slim_history_for_local` 丢整轮、云端分支保留最近 8 条，丢的是**整轮**且已用尾部提示明示；
  OpenClaw 要防的"有损散文摘要丢掉精确标识符"这条风险路径在我们这里不存在。
  对应的真实风险是"模型引用它已经看不见的数字"——由上面的整行保留 + 禁止凭记忆复述覆盖。
- [ ] 压缩**前**一行提示（提醒模型把要点写进记忆）：未做，属措辞级改动，随时可插队。

### 🟡 P2 — 任务级成本可见性

**现状**：预算守卫已上线但是**静默收口**；用户烧 token 时未必看得见（近期刚修过 tps/TTFT 假数字）。

**做法**：
- 会话状态里暴露"本轮已用输入 token / 预算比"，接近阈值给**显式提示**而非悄悄收口；
- 失败重试的消耗计入可见指标（重试是隐形烧钱大户——现有 `turn_input_tokens` 已含重试的 prompt）。

**验收**：一次长任务结束后，用户能看到"这轮花了多少、花在哪（几次重试）"。
**数据源**：`context_stats` 的 `turn_input_tokens` / `gen_tokens`（现成，无需新增埋点）。

### ✅ P3 — 旧工具结果的"可丢弃"精化 · **2026-09-29 已完成（第 3 步）**

**原现状**：基础回收已上线（保最近 6 条、≥1500 字折叠），但一刀切。

**已做的**（`agent/loop.py: _fold_params` / `_tool_name_by_call_id`）：按工具类别分档——
从 assistant 的 `tool_calls` 建 `call_id → 工具名` 映射（native 与围栏两条路径都写回
assistant 消息，所以两种协议都能认），再按类别选阈值：

| 类别 | 工具 | 折叠门槛 | 保留开头 | 保护窗 |
|---|---|---|---|---|
| 可丢弃（看一眼就够、随时可重拿） | `read_file` `list_dir` `search_files` `tavily_search` `bing_search` `web_search` `dokobot_search` | ≥700 字符 | 250 | 最近 6 条 |
| 保久（数字即结论 / 重拿代价高） | `mx_query` `ak_finance` `delegate_task` | ≥2500 字符 | 900 | 最近 **12** 条 |
| 其他（默认） | `run_cmd` 等 | ≥1500 字符 | 400 | 最近 6 条 |

折叠标记里还写上了**是哪个工具的结果**（"需要完整数据可重新调用 read_file"），
模型据此知道怎么重拿。

**验收证据**（`sidecar/tests/test_thin_loop.py` 的 3 条新用例）：
- 分档正确（读文件 1000 折、行情 2000 不折、行情 4000 折且留 900 字符、run_cmd 走默认档）；
- 同为 1200 字符且同样旧：读文件被折、行情类保持原样（"更久"是可机检的）；
- **50 轮长对话出现下降段**：60k 字符 → 折 47 条后大幅下降（在 compaction 阈值兜底之前）；
- **A/B**：回退 `loop.py` 后这 3 条**全红**（旧实现一刀切 1500/400），新实现全绿；
  全量 `1197 passed, 1 skipped`（CI 同款 venv）。

**边界**：保护窗是"条数"而非时间/轮次——一个超长工具轮的末端 6（或行情类 12）条不折，
再往前的才折；这是有意的（模型刚看过的数据不动）。

### 🟢 P3 — Loop 级故障注入测试（**前置项，见第四节顺序**）

> **进度（2026-09-29）**：场景③「预算耗尽」已做——`sidecar/tests/test_budget_guard.py` 进 CI。
> 受控实测**当场查出一个真 bug**：本地引擎路径的输入 token 计数只取 `timings.prompt_n`
> （本次新评估量），漏掉了缓存的 `cache_n`（两者相加才是完整 prompt，见 `context_stats.py:346`），
> 于是 6 步只记 6797（真实约 4 万）→ **守卫在本地等于永不触发**。已修（`record_usage` 取
> `prompt_n + cache_n`），并用真实引擎复测：越线后下一轮触发收口、回合在 **5 步**（而非 40 步）结束、
> `_budget_wrapped=True`。另一个附带的收益：上下文面板的"真实输入"校准也一并变准确了。
> **①② 也已完成（同日）**：`sidecar/tests/test_fault_injection.py` 三例——
> ①a 同参空转（停滞闸门在 7 步收口，上限 40）；①b 同错升级（**4 步**交回，交付文案含
> 「已停止重试…交回给你」）；② 假成功（收口轮空正文 → 交付**已收集数据**而非空/碎片）。
> **第 0 步（故障注入台架）三场景齐备。**
>
> 第二个真 bug（①b 顺带查出）：同错扫描的失败判据只认 "Error"/"⛔"，而 `read_file`
> 缺文件返回「**错误：文件不存在**」等中文文案 → 中文报错的工具永不计入失败，同错升级
> 形同虚设。已与 `verify_failed` **统一为唯一判据** `tool_exec._looks_like_tool_failure`
> （含中文：错误/不存在/未找到/权限不足），两处共用、防再次漂移。
>
> 方法教训：弱断言会让 A/B 失去判别力——①b 最初写「含'文件不存在'即通过」，旧判据下
> 也能靠数据兜底满足它，`旧代码 A/B` 才暴露出来；收紧为只认升级文案后，旧判据下该测试
> **确实失败**。**每条闸门测试都必须用旧代码验证它会红。**

### 🟢 P3 — Loop 级故障注入测试（**前置项，见第四节顺序**）

**现状**：各组件有单测，但没有"Loop 级"的系统性回归。

**做法**：固定 3 个场景进 CI——
1. 死循环（同错连续）→ 预期在阈值轮内 ESCALATE；
2. 假成功（空交付）→ 预期收口而不交付空正文；
3. 预算耗尽 → 预期先收口、再停手。
**断言**：三者都**不得跑满 `MAX_STEPS` 才发现**。

### 🟢 P3 — 提示词里的 Loop 意识（低风险，可随时插队）

**现状**：硬规则管时间/语言/数据诚实/承诺；没有一条告诉模型"你处于有步数与预算上限的循环里，
反复失败应当主动说卡住"。唯一相关的一句是"每阶段 token 预算 ≤ 上下文窗口 30%"。

**做法**：在交付纪律旁加一行——反复失败时主动报告卡点并建议交回用户，而不是硬撑到上限。

## 三、按场景不做（写清理由，附时机）

| 项 | 不做的理由 | 何时翻转 |
|---|---|---|
| git worktree 多 Agent 并行 | 桌面助手以对话为主，串行够用；worktree 引入隔离与合并复杂度 | **当"让辣条跑长任务"落地时**（cron 修 CI / 财务流水线）——那时隔离与 P1 一起变成必需 |
| LLM-as-judge 作主验证 | 本地模型不可靠；文章同观点（优先确定性验证） | 云端模型做专用裁判且已验证稳定性后 |

### 施工约束（2026-09-29 三次教训，写死）

1. **闸门不许吞记账**：任何"就地 return"之前，本轮的检索计数/信息增量必须已完成
   （同日 CI 抓到：同错升级第一版在第 3 个并行调用处 return，`_search_used` 停在 0）。
2. **基线必须取在改动之前**：不能用"失败集合相同"证明无回归（我当天犯过：基线取在自己改动之后）。
3. **验证环境用 CI 同款**：`venv + pip install -r sidecar/requirements-test.txt`，
   `python -m pytest sidecar/tests -q`（临时瘦环境会漏检；当天因此放过两个真失败）。
4. **每个闸门先证明它会失败**：新测试必须在**旧代码**上跑失败、在新代码上通过（A/B 对照）。
5. **生效分级**：建议 → 收口 → 硬闸，逐级观察后再升级。
6. **一个返回值别服务两种相反诉求**（第 1b 轮教训）："一行都没丢（小体量，不该动）"与"单行极长
   （必须动）"曾共用同一分支 → 小内容被劈开加噪音标记。判据要显式分开（`_KEEP_HARD_MAX`），
   并且 A/B 要打在**真实调用点**上（改函数 + 走 hook 各测一遍），只测函数体漏掉集成面。

## 二、缺口（按优先级；每条含验收与风险）

### 🔴 P1 — 任务级验证器（"这轮算不算完成"的机械定义）

**现状**：每步工具有自检，但"任务是否完成"仍主要信模型自报（刚修过"自称已完成、正文 0 字"）。

**缺口**：没有对**目标**的机械验收——文章 CI 例子里的"测试全绿才算完"在辣条没有对等物；
也没有"不得通过破坏被验对象达成目标"的防线（删掉失败的测试让 CI 变绿）。

**做法（四条约束，缺一不可）**：

1. **白名单制**：只有能给出可机检终点的任务类型才启用——写文件（产物存在 + 可打开 + 结构下限）、
   修复类（指定测试由红转绿）、指定格式交付（结构/字段校验）。
   **开放问答明确"无验证器"**（"帮我分析今天大盘"没有机械验收，不得强行套）。
2. **两级生效**：先只做**提示与收口**（发现未达标就提醒/重采一次），跑够一段时间再评估是否升硬闸。
   *理由：本仓库新增闸门的第一版都误伤过（plan-only 闸拦正常短答、饱和闸误判覆盖查询、
   碎片闸被思考字数蒙蔽、同错升级吞记账）——直接上硬闸就是第五次。*
3. **反作弊条款**：验证期间**被验对象的完整性**纳入校验——测试/断言/被检查文件被删除或改写
   → 直接判 ❌ 并交回用户（对应文章的"目标误设"失败模式）。
4. **不吞记账**：任何新闸门都不得跳过本轮的检索计数/信息增量（见第四节施工约束）。

**验收**：
- 构造三类任务各 1 例（写文件、跑测试修复、指定格式交付）；达标 / 未达标 / 作弊（删测试）三条路径都可复现；
- 开放问答（无验证器）**零行为变化**；
- 未达标时**不交付**"我已完成"，而是重采一次 → 仍不行则交回用户（复用现有硬升级通道）。

**不动的后果**：幻觉成功换个形态还会回来。

**对照主流（2026-09-29 核查）**：ZCode / OpenClaw / Hermes 三家均**没有**任务级验收器——
它们的「验证」是 agent 自己跑测试/构建 + 人在环审批 + skills（Superpowers 那类提示词 SOP）。
含义有两层：① 辣条做 P1 会**领先于**主流；② **没有现成作业可抄**，所以上面四条约束
（尤其「白名单」与「两级生效」）不是保守，而是必要的安全垫。

### 🟡 P2 — 验证结果反哺停止条件（组件咬合）· 建议**先做这一项**

**现状**：`verify_failed` 影响当轮话术，但不直接改变"停不停"——连续验证失败与单次失败待遇相同。

**做法**：连续 N 次 verify ❌ 且无信息增量 → 并入**已存在的硬升级通道**（与同错升级共用 `_scan_tool_failures` 的计数面，不新造机制）。

**验收**：构造"一直写错文件"的场景，应在 N 轮内交回用户，**而不是跑满 40 步**。
**风险**：低（复用已验证的通道）；注意仍要"按轮去重 + 不吞记账"。

---

### 🟡 P2 — 压缩可靠性（2026-09-29 对照主流后新增）

**现状**：compaction 只是「压完就继续」（`agent/plugins/builtin.py:162` 各分支均 `return payload`，
没有质量校验、也没有失败回退）；压缩前**没有**提醒模型把要点存档（grep 无此提示）。

**对照**：OpenClaw 在这块是三者里最讲究的——压缩保持 tool_call/结果**配对**；`safeguard` 模式做
**摘要质量审计**（必需标题/待办/精确标识符必须在）；不合格只给有限次修正，**仍不合格就放弃压缩、
保留原历史**；压缩前主动提醒 agent 把要点写进 memory 文件。

**做法**：
- [ ] 压缩后做最小校验：被压缩段里的**精确标识符/数字/待办**必须在摘要里存活（抽样几个，不追求全量）
- [ ] 校验不过 → **放弃这次压缩、保留原历史**（宁可不压，也不要把任务压缩丢）
- [ ] 压缩前一行提示：提醒模型把当前要点写入记忆（开放问答尤其需要）

**验收**：构造「压缩后再问前面提过的标识符」，答案仍正确；压缩失败时行为与「未压缩」一致。
**成本**：小（校验规则可先只覆盖数字与文件名）。

### 🟡 P2 — 任务级成本可见性

**现状**：预算守卫已上线但是**静默收口**；用户烧 token 时未必看得见（近期刚修过 tps/TTFT 假数字）。

**做法**：
- 会话状态里暴露"本轮已用输入 token / 预算比"，接近阈值给**显式提示**而非悄悄收口；
- 失败重试的消耗计入可见指标（重试是隐形烧钱大户——现有 `turn_input_tokens` 已含重试的 prompt）。

**验收**：一次长任务结束后，用户能看到"这轮花了多少、花在哪（几次重试）"。
**数据源**：`context_stats` 的 `turn_input_tokens` / `gen_tokens`（现成，无需新增埋点）。

### 🟢 P3 — 旧工具结果的"可丢弃"精化

**现状**：基础回收已上线（保最近 6 条、≥1500 字折叠）。

**做法**：加"可丢弃工具"名单（读文件/搜索类早期结果优先折叠；`mx_query` 这类**结果含数字**的
保持原样更久，因为丢失细节会直接导致数字引用错误）。

**验收**：50+ 轮长对话里，上下文占用曲线出现**下降段**（在 compaction 阈值之前）。

### 🟢 P3 — Loop 级故障注入测试（**前置项，见第四节顺序**）

> **进度（2026-09-29）**：场景③「预算耗尽」已做——`sidecar/tests/test_budget_guard.py` 进 CI。
> 受控实测**当场查出一个真 bug**：本地引擎路径的输入 token 计数只取 `timings.prompt_n`
> （本次新评估量），漏掉了缓存的 `cache_n`（两者相加才是完整 prompt，见 `context_stats.py:346`），
> 于是 6 步只记 6797（真实约 4 万）→ **守卫在本地等于永不触发**。已修（`record_usage` 取
> `prompt_n + cache_n`），并用真实引擎复测：越线后下一轮触发收口、回合在 **5 步**（而非 40 步）结束、
> `_budget_wrapped=True`。另一个附带的收益：上下文面板的"真实输入"校准也一并变准确了。
> **①② 也已完成（同日）**：`sidecar/tests/test_fault_injection.py` 三例——
> ①a 同参空转（停滞闸门在 7 步收口，上限 40）；①b 同错升级（**4 步**交回，交付文案含
> 「已停止重试…交回给你」）；② 假成功（收口轮空正文 → 交付**已收集数据**而非空/碎片）。
> **第 0 步（故障注入台架）三场景齐备。**
>
> 第二个真 bug（①b 顺带查出）：同错扫描的失败判据只认 "Error"/"⛔"，而 `read_file`
> 缺文件返回「**错误：文件不存在**」等中文文案 → 中文报错的工具永不计入失败，同错升级
> 形同虚设。已与 `verify_failed` **统一为唯一判据** `tool_exec._looks_like_tool_failure`
> （含中文：错误/不存在/未找到/权限不足），两处共用、防再次漂移。
>
> 方法教训：弱断言会让 A/B 失去判别力——①b 最初写「含'文件不存在'即通过」，旧判据下
> 也能靠数据兜底满足它，`旧代码 A/B` 才暴露出来；收紧为只认升级文案后，旧判据下该测试
> **确实失败**。**每条闸门测试都必须用旧代码验证它会红。**

### 🟢 P3 — Loop 级故障注入测试（**前置项，见第四节顺序**）

**现状**：各组件有单测，但没有"Loop 级"的系统性回归。

**做法**：固定 3 个场景进 CI——
1. 死循环（同错连续）→ 预期在阈值轮内 ESCALATE；
2. 假成功（空交付）→ 预期收口而不交付空正文；
3. 预算耗尽 → 预期先收口、再停手。
**断言**：三者都**不得跑满 `MAX_STEPS` 才发现**。

---

### 🟢 P3 — 提示词里的 Loop 意识（低风险，可随时插队）

**现状**：硬规则管时间/语言/数据诚实/承诺；没有一条告诉模型"你处于有步数与预算上限的循环里，
反复失败应当主动说卡住"。唯一相关的一句是"每阶段 token 预算 ≤ 上下文窗口 30%"。

**做法**：在交付纪律旁加一行——反复失败时主动报告卡点并建议交回用户，而不是硬撑到上限。

## 四、施工顺序（与上一版不同的两点：台架前置、咬合先行）

```
第 0 步（先做）  P3 故障注入 3 场景进 CI        ← 先有台架再上闸门
第 1 步          P2 连续 verify ❌ → 并入硬升级   ← 最小改动，直接补"验证与停止"的咬合
第 2 步          P1 任务级验证器（白名单 + 两级 + 反作弊 + 不吞记账）
第 3 步          P3 可丢弃工具名单（回收精化）
第 4 步          P2 成本可见性（数据源现成）
随时可插队        P3 提示词 Loop 意识（一行）
```

### 施工约束（2026-09-29 两次教训，写死）

1. **闸门不许吞记账**：任何"就地 return"之前，本轮的检索计数/信息增量必须已完成
   （同日 CI 抓到：同错升级第一版在第 3 个并行调用处 return，`_search_used` 停在 0）。
2. **基线必须取在改动之前**：不能用"失败集合相同"证明无回归（我当天犯过：基线取在自己改动之后）。
3. **验证环境用 CI 同款**：`venv + pip install -r sidecar/requirements-test.txt`，
   `python -m pytest sidecar/tests -q`（临时瘦环境会漏检；当天因此放过两个真失败）。
4. **每个闸门先证明它会失败**：新测试必须在**旧代码**上跑失败、在新代码上通过（A/B 对照）。
5. **生效分级**：建议 → 收口 → 硬闸，逐级观察后再升级。
